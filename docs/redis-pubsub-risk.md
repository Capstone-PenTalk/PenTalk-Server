## 리스크 분석

### 1. Subscriber 연결 끊김 중 메시지 유실

| 항목 | 내용 |
|------|------|
| 원인 | Redis Pub/Sub은 fire-and-forget 구조. subscriber가 연결되어 있지 않은 순간 publish된 메시지는 영구 유실 |
| 발생 조건 | 서버 재시작, 네트워크 순단, Redis 연결 재시도 중 |
| 영향 범위 | 해당 시간대에 전송된 DM 전부 |
| 현재 대응 | `redisPubSub.js`에 `reconnecting` 이벤트 로그만 존재, 재전송 없음 |

### 2. Redis 서버 자체 장애

| 항목 | 내용 |
|------|------|
| 원인 | Redis 프로세스 다운, OOM, 네트워크 단절 |
| 영향 범위 | 세션 조회, DM 전송, 판서 브로드캐스트 전체 불가 |
| 현재 대응 | ioredis 자동 재연결(기본값) + 에러 로그. 서킷브레이커 없음 |

## 이번 스프린트 결정: 유실 수용

### 수용 근거

- DM은 **수업 보조 채널**로, 한 두 메시지 유실이 수업 진행에 치명적이지 않음
- 판서(`draw_event`)는 Redis를 거치지 않고 **Socket.IO 직접 브로드캐스트** — 유실 없음
- 현재 단일 Redis + 소규모 동시 접속 환경에서 장애 발생 빈도 낮음

### 향후 대응 옵션 (우선순위 순)

| 옵션 | 효과 | 비고 |
|------|------|------|
| Redis Streams 전환 | 메시지 영속화 + consumer group으로 재처리 가능 | 구조 변경 필요 |
| 클라이언트 재전송 | 수신 ACK 없으면 재전송 | 프론트 협의 필요 |
| Redis Sentinel / Cluster | Redis HA 구성으로 단일 장애점 제거 | 인프라 비용 증가 |

## 판서 유실 리스크 (별도)

판서(`draw_event`)는 Redis를 거치지 않으므로 **Redis 장애와 무관**.
단, 다중 인스턴스 환경에서 Socket.IO sticky session 미적용 시 같은 룸의 소켓이 다른 인스턴스에 분산되면 브로드캐스트 누락 발생 가능.
→ 현재는 단일 인스턴스 운영 기준. 다중 인스턴스 판서는 Redis Adapter 도입 필요.
